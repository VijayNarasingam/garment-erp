# POS Thermal Bill Printing - Design Specification

- Date: 2026-11-11
- Status: Draft for review
- Feature: Silent 80 mm thermal bill printing with an in-app printer selection, a configurable bill template, and browser-print fallback
- Repo: `garment-erp`

## 1. Summary

Today the POS posts the invoice and opens a receipt modal. The **Print** button calls `window.print()`, which prints the HTML receipt through `#print-root` at 80 mm. Every bill therefore opens the Windows print dialog, and the operator has to pick the thermal printer each time. The same PC also has a label/barcode printer, so choosing the wrong device is a real risk.

This feature adds a small local Windows print agent. The app builds the receipt and the ESC/POS byte stream, sends it to `http://127.0.0.1:17890/print`, and the agent writes it as a raw job to the selected printer. Normal billing then prints silently, with configurable copies and auto-cut. The existing browser print path remains as an automatic fallback, so billing is never blocked by printing.

The receipt content is business-wide and stored in the database. Printer selection, auto-print, copies, paper width, and font size are per billing PC and stored in `localStorage`.

## 2. Current State

- `PosPage.tsx` builds `receiptBody`, renders it on screen, and portals a copy into `#print-root`.
- `window.print()` is the only print action. It always opens the browser/Windows dialog.
- `index.css` already contains the 80 mm print pipeline: `#print-root` is hidden on screen and is the only visible element in `@media print`.
- The receipt currently shows shop name, branch name, address, phone, GSTIN, bill number, date, customer, cashier, item name/SKU/quantity, line amount, total, payment method, paid amount, and the thank-you note.
- The business entity already has `thankYouNote`, GSTIN, state code, round-off settings, return/exchange windows, and `settingsJson`.
- There is no UPI ID, no receipt terms, no receipt field toggles, and no printer settings.
- `InvoiceResponse` exposes `hsnCode`, `taxRate`, `taxInclusive`, `taxableAmount`, `taxAmount`, `lineTotal`, `discountAmount`, `charges`, `payments`, `paidAmount`, and `balanceAmount`.
- Offline bills are queued in IndexedDB. `OfflineSale` stores the sale request and total, but **not** the product display names, so the current offline receipt falls back to generic item labels.
- The A4 invoice PDF is generated by `InvoicePdfService` and is separate from the 80 mm receipt.

## 3. Goals

1. Select the bill printer once per billing PC from an in-app dropdown.
2. Print silently after a sale, either automatically or with one click.
3. Print 1-3 copies per bill; auto-cut after each copy.
4. Mark every reprint as `DUPLICATE`.
5. Let the business choose what appears on the bill, with a live paper-width preview.
6. Print an accurate GST bill: GSTIN, taxable value, HSN (optional), and CGST/SGST or IGST.
7. Print a dynamic UPI QR for the bill amount using the shop's UPI ID and payee name.
8. Keep the existing browser print as a fallback when the agent is missing, offline, or fails.
9. Never block billing. The invoice is posted before any print attempt.
10. Print offline bills too, even when the server is unreachable.
11. Leave the existing mobile billing layout and browser print behaviour intact.

## 4. Non-Goals

- Label/barcode printing. The label printer can be recorded for future use, but v1 does not print labels.
- Printing from the server, a cloud relay, or a different PC.
- Multiple receipt templates or per-user templates.
- A4 invoice PDF redesign.
- Cash drawer kick.
- Receipt languages other than English.
- Changing the backend overpayment rule. The receipt can display change if it ever exists, but the backend currently rejects payments above the total.
- Printing return/refund receipts. Only sale, offline sale, and exchange receipts are in scope.

## 5. Architecture

```text
Billing PC browser
  ReceiptModel (invoice/offline/exchange + business + local prefs)
        |
        +--> ESC/POS bytes (frontend)
        |        |
        |        v
        |   POST http://127.0.0.1:17890/print  (base64 bytes + printer + copies)
        |        |
        |        v
        |   PowerShell agent -> Windows spooler (RAW) -> USB 80 mm printer
        |
        +--> ReceiptDocument -> #print-root -> window.print()  (fallback)
```

Business-wide content settings:

```text
React Settings page -> PUT /api/business -> MySQL/H2 businesses table
```

Per-PC settings:

```text
React app -> localStorage['garment.print.prefs.v1']
```

### 5.1 Key Decision: Render ESC/POS in the frontend

The browser builds the ESC/POS byte stream. The agent is a dumb raw-byte spooler.

Reasons:

- One layout implementation serves the ESC/POS print, the on-screen preview, and the browser fallback.
- The PowerShell agent stays small and does not need to understand GST, discounts, templates, or QR data.
- Paper output and preview can be kept visually and structurally aligned.
- Template changes do not require reinstalling the agent.

Trade-off: the browser must sanitize text to the printer code page and calculate column widths. That logic is isolated in one module and unit tested.

## 6. User Flows

### 6.1 One-time setup per billing PC

1. An administrator runs `printer-agent\install.ps1` from an elevated PowerShell.
2. The installer copies the agent, creates the auto-start task, starts it, and prints the pairing code.
3. In **Settings > Bill print**, the operator pastes the pairing code and clicks **Connect**.
4. The operator clicks **Refresh printers**, chooses the 80 mm thermal printer, paper width, font size, copies, and auto-print preference.
5. The operator clicks **Test print**, checks the paper, QR, and cut, then enables **Print bills automatically**.
6. Business content (UPI ID, terms, field toggles) is saved once with **Save bill print settings**.

### 6.2 Normal sale

1. The cashier charges the bill. The invoice is committed on the server.
2. The receipt modal opens.
3. If auto-print is on and an agent printer is configured, the app sends the receipt to the agent asynchronously. The modal shows `Sending to <printer>...`.
4. On success, the modal shows `Sent to <printer>` and a success toast.
5. On failure, the modal shows a red inline error with **Retry** and **Browser print**. Auto-print failure does **not** open a dialog, because that would block the next bill.
6. If auto-print is off, the cashier clicks **Print**. That uses the agent when configured. If the agent is completely unreachable (nothing was sent), manual print opens the browser dialog once. If the agent accepted the request but returned an error or timed out, the app shows **Retry** and **Browser print** instead of auto-opening the dialog, to avoid duplicate paper.
7. If no agent/printer is configured, **Print** uses the browser print dialog directly.

### 6.3 Reprint

1. The cashier opens **Bill history**, opens an invoice, and clicks **Print**.
2. The app loads the invoice, builds the receipt with the current template, and sends it to the agent with `duplicate: true`. Reprints use the current business template settings, not a snapshot of the original bill.
3. The paper starts with a bold centred `*** DUPLICATE ***` line and the job name ends with `[DUP]`.
4. A reprint always prints **1 copy**, regardless of the configured copies setting.
5. If the agent is unavailable, the browser fallback also shows `*** DUPLICATE ***`.

### 6.4 Offline bill

1. When the server is unreachable, the POS queues the sale and shows the offline receipt.
2. At queue time the app stores a `ReceiptSnapshot` on the `OfflineSale`. This is the serializable part of `ReceiptModel` (items, totals, tax groups, payments, customer, cashier, invoice number, created time), excluding per-PC print preferences.
3. The agent is local, so the bill can still print while the server is down.
4. The receipt shows `OFFLINE BILL - pending sync` and a short offline ID instead of a server invoice number.
5. Older queued sales without a snapshot still print using the request items, with generic item labels. They are not blocked.

### 6.5 Mobile and tablet

- Below 768 px, the printer section in Settings is replaced by a short note: direct thermal printing is available on the billing desktop; browser print can still be used.
- Auto-print is ignored on mobile because `127.0.0.1` would be the phone, not the billing PC.
- The existing responsive billing layout and receipt modal are unchanged.

## 7. Receipt Model

The app normalizes every source into one model before rendering. The model is serializable and is also stored for offline bills.

```ts
type ReceiptKind = 'sale' | 'offline' | 'exchange'
type PaperWidth = 80 | 58
type FontSize = 'small' | 'normal' | 'large'

interface ReceiptModel {
  kind: ReceiptKind
  duplicate: boolean
  cancelled: boolean
  paperWidth: PaperWidth
  fontSize: FontSize
  invoiceNo: string
  invoiceDate: string
  shop: {
    name: string
    branchName: string
    addressLines: string[]
    phone?: string
    gstin?: string
    gstEnabled: boolean
  }
  customer?: { name: string; phone?: string; gstin?: string }
  cashier?: string
  items: ReceiptItem[]
  charges: { name: string; amount: number }[]
  totals: {
    subtotal: number
    discountTotal: number
    taxableAmount: number
    taxTotal: number
    roundOff: number
    total: number
    paidAmount: number
    balanceAmount: number
  }
  payments: { method: string; amount: number }[]
  taxGroups: { rate: number; taxable: number; tax: number }[]
  interState: boolean
  exchange?: {
    originInvoiceNo: string
    credit: number
    due: number
    returnedItems: { name: string; quantity: number; amount: number }[]
  }
  upi?: { vpa: string; payeeName: string; amount: number; note: string }
  terms?: string
  footer: string
  offlineNote?: string
}

interface ReceiptItem {
  name: string
  sku?: string
  size?: string
  color?: string
  hsnCode?: string
  quantity: number
  unitPrice: number
  discountAmount: number
  taxRate: number
  taxInclusive: boolean
  lineAmount: number
  meta?: string
}
```

### 7.1 Source mapping

| Receipt field | Source |
| --- | --- |
| `invoiceNo` | `invoice.invoiceNo`; offline: `OFFLINE-<first 8 of offlineId>` |
| `cancelled` | `invoice.status === 'CANCELLED'`; offline: `false` |
| `invoiceDate` | `invoice.invoiceDate` plus local time from `postedAt`; offline: `createdAt` |
| `shop` | Business name/GSTIN/address; branch address/phone/GSTIN override when present |
| `customer` | `invoice.customerName`/`customerPhone`/`customerGstin`; hide the customer block when the toggle is off, unless the customer has a GSTIN |
| `cashier` | `invoice.createdByName`; offline snapshot from the logged-in user |
| item name | `invoice.items[].productName` |
| item meta | SKU, size, colour, HSN, combined on one or two wrapped lines |
| item rate | `unitPrice` |
| item discount | `discountAmount` (item discount plus allocated bill-discount share) |
| item line amount | `lineTotal` |
| charges | `invoice.charges[]` names and amounts |
| `discountTotal` | `invoice.itemDiscount + invoice.billDiscount` |
| `taxableAmount` | `invoice.taxableAmount` |
| `taxTotal` | `invoice.taxTotal` |
| `roundOff` | `invoice.roundOff` |
| `total` | `invoice.total` |
| payments | `invoice.payments[]` method + amount; use readable labels: Cash, Card, UPI, Bank transfer, Cheque, Store credit, Exchange credit |
| paid/balance | `invoice.paidAmount` / `invoice.balanceAmount` |
| terms | `business.receiptTerms` or the generated default |
| footer | `business.thankYouNote` |

Important display rule: the backend stores `InvoiceItem.discountAmount` as item discount **plus** the allocated share of the bill discount. The receipt must not print the bill discount again as a separate total. It prints one `Discounts` summary line equal to `itemDiscount + billDiscount`, and per-item discounts sum to the same value.

Line amount rule: print `lineTotal` (the line value after all discounts). For exclusive-tax lines this is the pre-tax line value and GST is added in the totals; for inclusive-tax lines it already contains GST. Do not add `taxAmount` again on the item line; the tax summary explains the tax within or on top of the line values. This keeps line values consistent with `invoice.subtotal` and avoids double-counting inclusive tax.

`receiptShowItemRate` and `receiptShowItemDiscount` hide only the per-line rate/discount text. The summary `Discounts` line still prints when the total is non-zero, so the bill reconciles.

If the customer has a GSTIN, the customer name/GSTIN block and HSN are printed even when `receiptShowCustomer` or `receiptShowHsn` is off. B2B tax invoices must identify the buyer and the goods.

### 7.2 Tax summary

When `gstEnabled` is true:

1. Group taxable items by `taxRate`; add taxable charges grouped by their `taxRate`.
2. Print one `Taxable value` line from `invoice.taxableAmount`.
3. For each rate, print `CGST <rate/2>%` and `SGST <rate/2>%` when intra-state, or `IGST <rate>%` when inter-state.
4. Split each group's tax as `cgst = round(tax / 2)` and `sgst = tax - cgst` so the pair sums exactly to the group tax.
5. If the sum of group taxes differs from `invoice.taxTotal` by up to 0.05, adjust the largest group so the printed tax lines add up exactly.

Intra-state vs inter-state: compare `invoice.placeOfSupplyStateCode` with the branch state code, falling back to the business state code. Equal or missing => intra-state; different => inter-state.

HSN:

- Printed under the item name when `receiptShowHsn` is on.
- Forced on when the customer has a GSTIN, so B2B bills always show HSN.
- Never printed when GST is disabled.

When `gstEnabled` is false:

- Do not print GSTIN, HSN, taxable value, or tax lines.
- Print subtotal, discounts, charges, round-off, total, and payments only.

### 7.4 58 mm layout (32 columns)

- Same sections, narrower columns.
- Item block:
  ```text
  Cotton Kurta
   2 x 1,299.00            2,498.00
   Disc -100.00
  ```
- Long names wrap; never truncate the amount. If a name is longer than the width, wrap it; if it is longer than 3 lines, truncate with `...`.
- QR module size 3 instead of 4.
- If the printer only supports 80 mm, the 58 mm option has no effect; this is a hardware limitation documented in the agent README.

### 7.5 Column widths and font sizes

| Paper | Small | Normal | Large |
| --- | --- | --- | --- |
| 80 mm | 64 cols (Font B) | 48 cols (Font A) | 48 cols, double height |
| 58 mm | 42 cols (Font B) | 32 cols (Font A) | 32 cols, double height |

- Normal is the default.
- Large uses `GS ! 0x01` (double height only), so the column count does not halve.
- HTML preview uses the same character count with a monospace font and the selected paper width.

### 7.6 Text and currency rules

- Receipts are English-only.
- Encode as CP437 / ASCII. Replace `₹` with `Rs.`, curly quotes with straight quotes, en/em dashes with `-`, and unsupported characters with `?`.
- Strip ASCII control characters (`0x00-0x1F`, `0x7F`) from every text field before encoding. Only the ESC/POS builder may emit command bytes; product names, terms, and customer data must never be able to inject printer commands.
- Amounts use Indian grouping and two decimals: `1,23,456.00`.
- Line items use plain numbers. The total and UPI line use `Rs.` (`TOTAL Rs.3,619.00`, `Scan to pay Rs.3,619.00`).
- Trim trailing spaces, collapse repeated blank lines, and never emit a line wider than the column count.

### 7.7 UPI QR

- Enabled only when all of these are true: `receiptShowUpiQr` is on, `business.upiId` is non-blank, and the payable amount is greater than zero.
- Payable amount: invoice total for a sale/offline bill, or `exchange.due` for an exchange.
- Payee name: `business.upiPayeeName` or the business name.
- URI:
  ```text
  upi://pay?pa=<url-encoded vpa>&pn=<url-encoded payee>&am=<amount with 2 decimals>&cu=INR&tn=<url-encoded invoice no>
  ```
- Use native ESC/POS QR commands (`GS ( k`) for direct printing. Use the bundled `qrcode` library to render the same URI as a data URL for the HTML preview and browser fallback.
- QR settings: model 2, error correction M, module size 4 at 80 mm / 3 at 58 mm, centred.
- The QR prints whenever it is enabled and the payable amount is positive, even if the bill is already fully paid. It is a convenience for the customer, not a demand for payment.
- If the printer ignores the QR command, the rest of the bill still prints. The test print is the check for hardware support.

### 7.8 ESC/POS command set

- `ESC @` initialise.
- `ESC t 0` select CP437.
- `ESC a 0/1/2` left/centre/right alignment.
- `ESC E 1/0` bold on/off.
- `GS ! n` size for the large mode.
- `ESC d n` feed.
- `GS V 66 0` feed and partial cut after each copy.
- `GS ( k` QR commands.
- No cash-drawer pulse in v1.
- Copies are written as repeated byte streams inside one spool job, with a cut after each copy.

Notes:

- Essential options default ON, as approved. SKU/size/colour/HSN default OFF because they are advanced and make the bill longer.
- `thankYouNote` remains the footer and is reused, not duplicated.
- If `receipt_terms` is blank, the app generates terms only for windows greater than zero: `Exchange within <exchangeWindowDays> days with this bill.` when `exchangeWindowDays > 0`, and `Returns within <returnWindowDays> days.` when `returnWindowDays > 0`. If both are zero, the terms block is omitted even when the toggle is on.
- If `upi_payee_name` is blank, the business name is used.
- If `receipt_show_upi_qr` is on but `upi_id` is blank, the Settings page shows a warning and the receipt omits the QR block.

Validation:

- `upi_id`: optional; trim; blank becomes `null`; otherwise must match `^[A-Za-z0-9._-]{2,64}@[A-Za-z0-9.-]{2,64}$` and be at most 100 characters. The local part may contain letters, digits, dot, hyphen, and underscore; the handle may contain letters, digits, dot, and hyphen. No spaces. The DTO pattern must allow an empty string (`^$|...`) so a blank form field can be normalized to `null`; the frontend sends `null` when blank.
- `upi_payee_name`: optional; trim; max 150.
- `receipt_terms`: optional; trim; max 500; blank becomes `null`.

Backend changes:

- `Business.java`: add the 13 fields with matching defaults.
- `BusinessDtos.BusinessResponse`: add the 13 fields.
- `BusinessDtos.UpdateBusinessRequest`: add the 13 fields with `@Size`/regex validation.
- `BusinessService.update`: persist and normalize the new fields.
- `BusinessService.toResponse`: return the new fields.
- `BusinessService.snapshot`: include UPI ID, toggles, and terms so the audit trail records receipt-template changes. Use null-safe values (for example `b.getUpiId() == null ? "" : b.getUpiId()`) because `Map.ofEntries` rejects nulls.
- Frontend `BusinessSettings`/`BusinessInfo` types and the settings form: add the fields; always send them on save.

The migration is additive and works on both H2 and MySQL 8. No backfill is needed. Existing bills reprint with the current template, which is expected.

### 8.2 Per-PC settings (localStorage)

Key: `garment.print.prefs.v1`

```json
{
  "version": 1,
  "agentUrl": "http://127.0.0.1:17890",
  "token": "",
  "printer": "",
  "labelPrinter": "",
  "autoPrint": false,
  "copies": 1,
  "paperWidth": 80,
  "fontSize": "normal"
}
```

- `agentUrl` defaults to loopback and is editable only under **Advanced**, for a non-default port.
- `token` is the pairing code. It is local only and never sent to the Garment ERP server.
- `printer` is the selected bill printer name exactly as Windows reports it.
- `labelPrinter` is saved for future label printing and is not used in v1.
- `autoPrint` defaults to `false` so a new PC does not print unexpectedly before setup. The setup card recommends turning it on after a successful test print.
- `copies` is clamped to 1-3.
- `paperWidth` is 80 or 58; default 80.
- `fontSize` is `small`, `normal`, or `large`; default `normal`.
- Changes save immediately. Business content still requires **Save bill print settings**.

```json
  "printer": "XP-80C",
  "bytes": 4821,
  "copies": 1,
  "warning": "Printer status is Offline. The job was queued by Windows."
}
```

Errors:

| HTTP | Code | Meaning |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | Missing/invalid printer, bytes, or copies |
| 401 | `UNAUTHORIZED` | Missing/wrong token |
| 404 | `PRINTER_NOT_FOUND` | Printer name does not exist |
| 413 | `PAYLOAD_TOO_LARGE` | Decoded bytes exceed 512 KB |
| 429 | `RATE_LIMITED` | More than 60 requests per minute |
| 500 | `PRINT_FAILED` | Spooler/WritePrinter failure |

Limits and validation:

- `copies` 1-3.
- Decoded payload max 512 KB; request body max 1 MB.
- Printer name max 220 chars; job name max 120 chars.
- `jobName` defaults to `Garment ERP Bill`.
- Requests are serialized; one print job at a time. A second request waits, then prints. This avoids interleaved bytes on the same device.
- Success means **Windows accepted the job**, not that paper physically came out. The app wording is `Sent to <printer>`.

### 9.3 Raw printing

PowerShell loads a small embedded C# helper that P/Invokes `winspool.drv`:

`OpenPrinter` -> `StartDocPrinter` with datatype `RAW` -> `StartPagePrinter` -> `WritePrinter` -> `EndPagePrinter` -> `EndDocPrinter` -> `ClosePrinter`.

- `WritePrinter` receives the decoded byte array. No text encoding or line wrapping happens in the agent.
- Copies are written as repeated streams in the same document, each ending with the cut command already present in the bytes.
- Before printing, the agent checks that the printer exists with `Get-Printer`.
- If `PrinterStatus` is not `Normal`/`Unknown`, the job is still submitted (Windows may queue it) and the response includes a `warning`.
- If `WritePrinter` fails, return `500 PRINT_FAILED` with the Win32 error message.

### 9.4 Installer

`install.ps1`:

- `#Requires -RunAsAdministrator`.
- Parameters: `-Port 17890`, `-AllowedOrigins "*"`, `-Force`, `-RotateToken`.
- Stops and removes an existing task before reinstalling.
- Copies `agent.ps1` to `%ProgramData%\GarmentERPPrinterAgent`.
- Creates or reuses `config.json` with port, allowed origins, token, and log settings. `-Force` resets; otherwise the existing token is kept.
- Generates a 32-character token with `[guid]::NewGuid().ToString('N')`.
- Adds a URL ACL for the current user:
  `netsh http add urlacl url=http://127.0.0.1:<port>/ user=<domain\user>`
- Creates a hidden Scheduled Task:
  - Name: `GarmentERP Printer Agent`
  - Trigger: at logon of the installing user
  - Principal: installing user, limited run level (the agent needs no admin at runtime)
  - Action: `powershell.exe -NoProfile -WindowStyle Hidden -ExecutionPolicy Bypass -File "<path>\agent.ps1"`
  - Settings: hidden, allow start on batteries, do not stop on battery, restart 3 times at 1-minute intervals, no execution time limit.
- Starts the task and polls `/health` for up to 10 seconds.
- Prints the pairing code and the next steps at the end.
- Writes the token to `%ProgramData%\GarmentERPPrinterAgent\token.txt` with an ACL for the current user and Administrators only, so the operator can retrieve it later.
- Grants the installing user Modify permission on the install folder and logs folder. The agent runs as that limited user and must be able to write its log and read its config.

`uninstall.ps1`:

- Stops and deletes the task.
- Removes the URL ACL.
- Removes the install folder unless `-KeepConfig` is passed.
- Does not remove printers or drivers.

`README.md` covers install, pairing, test print, port change, token reset, log location, and troubleshooting (`printer not listed`, `printer offline`, `access denied`, `port in use`, `task not running`).

### 9.5 Security

- Bind only to `127.0.0.1`. Never `0.0.0.0`.
- Validate the `Host` header: only `127.0.0.1:<port>` and `localhost:<port>`.
- Require `X-Print-Agent-Token` on `/printers` and `/print`. `/health` is public but contains no sensitive data.
- CORS: default `Access-Control-Allow-Origin: *` because the token is the gate and no cookies/credentials are used. If `allowedOrigins` is configured, echo only matching origins.
- Include CORS headers on every response, including 4xx/5xx errors, so the browser can read the real status instead of reporting a generic network failure.
- Allow headers `Content-Type, X-Print-Agent-Token`; methods `GET, POST, OPTIONS`.
- Respond to Chrome Private Network Access preflight with `Access-Control-Allow-Private-Network: true` when requested.
- Cap request size and rate. Reject invalid JSON and malformed base64.
- Never log receipt bytes, customer data, or the token. Log only job ID, printer, byte count, copies, duration, status, and error text.
- The token is stored in localStorage on the billing PC. It is a local print secret, not a payment credential. Any local user with access to the browser profile can read it; that is accepted for a single-shop billing PC.
- The agent never executes shell commands with printer names or job names. All printing goes through Win32 APIs with byte buffers.

### 9.6 Reliability

- Scheduled task restart on failure: 3 attempts, 1 minute apart.
- The agent wraps the listener loop in a top-level try/catch and restarts the listener after an unexpected exception.
- If the port is already in use, start-up fails and writes a clear log line; the task retries.
- Log rotation: one file per day, delete files older than 7 days, cap each file at 5 MB.
- A 10-second per-job timeout. On timeout, return `500 PRINT_FAILED`; do not retry automatically, to avoid duplicate paper.
- `/health` should respond in under 200 ms and must not enumerate printers.

### 10.3 Browser print provider

`PrintProvider` wraps the authenticated app and owns the hidden print host.

- It creates/uses `#print-root` on `<body>`.
- `printBrowser(model)`:
  1. Sets the current print model.
  2. Waits for the portal to paint (`requestAnimationFrame` twice or a short timeout).
  3. Calls `window.print()`.
  4. Clears the model on `afterprint`, with a timeout safety net.
- `printReceipt(model, { mode })`, where `mode` is `auto` or `manual` (the model already carries `duplicate`):
  - If an agent/printer is configured, build ESC/POS, POST to the agent, and return a typed result.
  - If the agent is unreachable before a request is accepted and `mode` is `manual`, call `printBrowser(model)` once and return a result with the original error attached.
  - If the agent accepted the request but returned an error or timed out, do **not** auto-open the browser dialog. Return the error so the caller can show `Retry` and `Browser print`, avoiding duplicate paper.
  - If no agent is configured and `mode` is `manual`, call `printBrowser(model)`.
  - If no agent is configured and `mode` is `auto`, do not open a dialog; return `NOT_CONFIGURED` so the receipt modal can show the setup hint.
  - For `mode: auto`, never open the browser dialog on failure; return the error so the receipt modal can show it.
- Only one browser print at a time. Disable the print button while a job is in flight.
- If `model.duplicate` is true, force `copies: 1`; otherwise use `prefs.copies`.
- Test print uses sample data, 1 copy, and `jobName = "Garment ERP Test Print"`.

### 10.4 Agent client

- Base URL from prefs, normalized to remove a trailing slash.
- `health`: 1.5 s timeout, no token.
- `listPrinters`: 3 s timeout, token header.
- `print`: 12 s timeout, token header, JSON body with base64. The client timeout is longer than the agent's 10 s job timeout so a slow spooler does not look like a network failure.
- Typed error: `{ code, message, status }`; network failure maps to `AGENT_UNREACHABLE`.
- Do not retry print automatically.
- On 401, clear the connected state and show the pairing prompt. Do not clear the token automatically; the operator may have mistyped the URL.
- On 404, refresh the printer list and show `Printer not found. Choose it again.`

### 10.5 Auto-print

- Triggered only from the success handlers after the invoice/offline sale is safely stored.
- Conditions: `prefs.autoPrint`, `prefs.printer`, `prefs.token`, and not mobile.
- Fire-and-forget from the billing flow; never `await` it before clearing the cart or showing the receipt.
- The receipt modal's status row reflects the result.
- One attempt per receipt. No retry loop.
- If the same receipt modal is reopened, do not auto-print again.

### 10.6 Status wording

- Printing: `Sending to <printer>...`
- Success: `Sent to <printer>` (green)
- Warning: `Sent to <printer> - printer reports <status>` (amber)
- Failure: `Could not print: <message>` (red) + `Retry` + `Browser print`
- No agent configured: `Direct printing is not set up on this computer.` + `Set up` link to Settings.
- Browser fallback: `Opening the browser print dialog...`

## 11. Error Handling Matrix

| Condition | Detection | App behaviour |
| --- | --- | --- |
| Agent not installed/running | `health`/`print` network error | Red status; manual print falls back to browser; auto-print shows inline error only |
| Wrong pairing code | 401 | `Pairing code not accepted`; prompt to re-enter; no fallback loop |
| Printer missing | 404 `PRINTER_NOT_FOUND` | Refresh list, ask to choose again; manual fallback allowed |
| Printer offline/paper out | 200 + warning | Amber `Sent - printer reports Offline/PaperOut`; do not retry |
| Print timeout | 12 s client timeout / 10 s agent timeout | Treat as failure; show `Print status unknown - check the paper before retrying`; no automatic retry |
| Payload too large | 413 | Show `Bill data is too large`; browser fallback |
| Rate limited | 429 | Show `Printer agent is busy`; retry button |
| Business settings save fails | API error | Toast; local prefs already saved |
| UPI QR on but no UPI ID | Settings validation | Warning in Settings; QR omitted from paper |
| Browser print blocked/cancelled | `window.print()` returns | No crash; receipt stays open |
| Mobile device | viewport <768 px | Direct print hidden; browser print remains |
| Old offline sale with no snapshot | missing field | Print generic item labels; do not block |

## 14. Risks and Assumptions

- **Printer QR support varies.** Some cheap ESC/POS printers ignore `GS ( k`. The test print is the gate. If a specific model cannot print QR, a future enhancement can rasterize the QR as a bitmap. This is not in v1.
- **Spooler acceptance is not physical confirmation.** The UI says `Sent`, not `Printed`. Paper-out/offline states are surfaced as warnings when Windows reports them.
- **Pairing code adds setup friction.** It is a one-time paste and protects raw printing from malicious web pages. The installer prints it and keeps a retrievable copy.
- **CP437 cannot render every product name.** English-only receipts are the requirement; unsupported characters become `?`. Tamil/other-script product names would need a graphics-based renderer later.
- **HTTPS/cloud -> loopback.** If the app is later served over HTTPS from a cloud host, Chrome may block or preflight `http://127.0.0.1` calls. The agent supports Private Network Access preflight, but a future cloud deployment may need a local HTTPS certificate or a desktop wrapper. Browser print remains the fallback.
- **Per-user printer visibility.** The agent runs as the installing Windows user at logon, so it sees that user's printers. If the shop changes the Windows user, reinstall/pair for that user. USB printers installed machine-wide are unaffected.
- **Offline settings can be stale.** An offline bill prints with the business settings cached in the app at that moment. It is not re-rendered with newer settings after sync.
- **Change is normally zero.** The backend currently rejects payments above the invoice total, so the `Change` line appears only if overpayment data exists. No billing logic change is included.

Assumptions:

- The billing PC runs Windows 10/11 with PowerShell 5.1.
- The 80 mm printer is ESC/POS compatible, supports auto-cut, and supports native QR commands. A 58 mm printer is optional.
- Each billing PC has one bill printer. The label/barcode printer is separate and is not used for bills in v1.
- The shop has a UPI VPA and payee name, and is happy to print the UPI QR on bills.
- The billing PC stays logged in as the installing Windows user. The agent starts at logon; logging out stops it and only the browser fallback remains.
- Auto-print is off until the operator enables it after a successful test print.
- A reprint prints one copy. Normal prints use the configured 1-3 copies.
- The A4 PDF remains the formal invoice document and is unchanged in v1.
